# 신규 글 작성 작업지시서

Stay Daytrevel에 새 글을 추가할 때 따라야 할 규칙입니다.
이 문서 하나만 읽고도 기존 글과 구분되지 않는 글을 쓸 수 있어야 합니다.

---

## 0. 작업 범위

**하는 일:** `src/content/` 아래에 `.mdx` 글 파일을 추가하는 것.

**함께 하는 일:** 글마다 이미지 2장이 필요합니다. 11장을 참고해
`scripts/image-data.json`에 항목을 추가하고 `npm run images`를 실행합니다.
(이 두 가지는 아래 금지 목록의 예외입니다.)

**하지 않는 일:** 아래 파일들은 이 작업에서 **수정하지 않습니다.**

- `src/layouts/`, `src/components/`, `src/pages/` 전체
- `src/content.config.ts`, `astro.config.mjs`, `package.json`
- `scripts/generate-images.mjs` (데이터만 넣고 스크립트 자체는 건드리지 않음)
- `public/styles/`

레이아웃·SEO·광고 코드는 별도 작업으로 진행 중이라, 위 파일을 건드리면 충돌합니다.
새 글을 위해 스키마 변경이 필요해 보이면 직접 고치지 말고 그 사실을 보고해 주세요.

**브랜치:** 별도 브랜치(예: `codex/content-tokyo-shinjuku`)에서 작업하고 그 브랜치로 푸시합니다.
`claude/` 로 시작하는 브랜치에는 푸시하지 않습니다.

## 1. 사이트 성격

숙소를 **추천**하는 사이트가 아니라, 숙소 지역을 **고르는 기준**을 설명하는 정보성 사이트입니다.
"어디가 좋다"가 아니라 "무엇을 확인하고 골라야 하는가"를 씁니다.

이 성격에서 벗어나는 글은 톤이 아무리 비슷해도 반려됩니다.

---

## 2. 컬렉션 구분

| 컬렉션 | 경로 | 다루는 내용 |
| --- | --- | --- |
| `stays` | `src/content/stays/` | 도시 안의 특정 지역에 숙소를 잡을 때의 위치 선택 기준 |
| `spots` | `src/content/spots/` | 가볼만한 곳·산책 코스 등 여행 정보 |

파일명은 영문 소문자 하이픈 slug이고, 그대로 URL이 됩니다.

- `stays`: `<도시>-<지역>-hotel-area.mdx` → `osaka-namba-hotel-area.mdx`
- `spots`: 장소를 설명하는 영문 slug → `yangjaecheon-walking-course.mdx`

## 3. frontmatter

`src/content.config.ts`의 zod 스키마로 **빌드 시 검증**됩니다. 형식이 틀리면 빌드가 실패합니다.

### stays

```yaml
---
title: '오사카 난바 숙소 지역 가이드 - 위치 선택 기준'
description: '오사카 난바에 숙소를 잡을 때 확인할 역 접근성, 이동 동선, 체크리스트를 정리한 정보성 가이드'
keyword: '오사카 난바 숙소'
affiliateReady: false
pubDate: '2026-08-21'
faq:
  - q: '...'
    a: '...'
  # 4개 이상 6개 이하
---
```

### spots

```yaml
---
title: '양재천 걷기 명소 - 강남·과천 산책 코스 총정리'
description: '양재천 산책로 구간별 특징과 접근 방법, 걷기 전 체크할 점을 정리한 여행 정보 가이드'
keyword: '양재천 걷기 명소'
pubDate: '2026-08-21'
faq:
  - q: '...'
    a: '...'
---
```

규칙:

- `affiliateReady`는 **stays 전용**입니다. spots에 넣으면 안 됩니다. 신규 글은 항상 `false`.
- `pubDate`는 작성일(`YYYY-MM-DD`)을 넣습니다. `updatedDate`는 신규 글에서는 생략합니다.
- `faq`는 **최소 4개, 최대 6개**. 스키마가 강제하므로 3개나 7개면 빌드가 깨집니다.
- 모든 문자열은 작은따옴표로 감쌉니다. 값 안에 작은따옴표가 필요하면 `''`로 이스케이프합니다.
- `title`은 `핵심 키워드 + 하이픈 + 부제` 형태. 40자 이내.
- `description`은 80~110자, `keyword`를 자연스럽게 포함.
- `keyword`는 실제 검색될 법한 짧은 구(2~4어절). 문장이 아닙니다.

## 4. 본문 구조

**본문에 `#`(H1)를 쓰지 않습니다.** 페이지가 `title`을 h1으로 이미 렌더링합니다.
FAQ도 본문에 쓰지 않습니다. frontmatter의 `faq`를 페이지가 별도 섹션으로 렌더링합니다.

순서는 고정입니다:

1. **도입 문단** (제목 없이 시작, 2~4문장)
   그 지역/장소가 어떤 곳인지 + 이 글이 무엇을 정리하는지.
2. **`##` 섹션 2개** — 역할은 고정, 제목에는 `keyword`를 넣습니다
   - 첫 번째 섹션: 대상 자체의 성격 → `## <keyword>의 특징`, `## <keyword> 코스의 특징`
   - 두 번째 섹션: 가는 방법과 동선 → `## <대상> 가는 길과 접근성`, `## <대상> 접근성과 이동 방법`
   - 각 섹션은 2문단. 한 문단은 3~5문장.
   - 네이버는 소제목에 들어간 키워드를 비중 있게 봅니다. 역할만 지키면 표현은
     자연스럽게 바꿔도 되지만, 키워드나 그 핵심어는 반드시 들어가야 합니다.
3. **`## 체크리스트`**
   - stays는 `## 숙소 체크리스트`, spots는 `## 방문 체크리스트`
   - 마크다운 표, 열은 `| 확인 항목 | 왜 확인해야 하나 |` 고정, 행은 6개
4. **마무리 고지 문단**
   ```html
   <p class="note">
   이 글은 ... 정보 제공 목적으로 작성했습니다. ... 다시 확인하시기 바랍니다.
   </p>
   ```
   stays는 "특정 숙소를 추천하지 않으며", "예약 전 최신 가격·재고·취소 규정 확인" 취지를,
   spots는 "현장 상황이 달라질 수 있으니 방문 전 최신 정보 확인" 취지를 담습니다.

전체 분량은 공백 포함 1,800~2,500자.

## 5. 네이버 SEO 규칙

이 사이트는 네이버 검색 유입을 주 타깃으로 합니다. 구글 기준과 다른 부분이 있습니다.

**키워드는 틈새(롱테일)로 잡습니다.**
`단풍 명소`, `가볼만한 곳` 같은 헤드 키워드는 대형 블로그·카페에 밀려 순위가 잡히지 않습니다.
`지역명 + 대상 + 목적`으로 좁혀 잡습니다.

| 피할 키워드 | 대신 잡을 키워드 |
| --- | --- |
| 단풍 명소 | 남한산성 단풍 |
| 억새 명소 | 하늘공원 억새 명소 |
| 가을 산책 | 서울숲 가을 산책 |
| 은행나무길 | 아산 곡교천 은행나무길 |

**키워드 배치**

- `title`은 `keyword`로 **시작**합니다. 네이버는 제목 앞쪽 단어에 가중치를 둡니다.
- `description`에 `keyword`를 그대로 한 번 포함합니다.
- 본문 **첫 문단 안에** `keyword`가 한 번 나와야 합니다.
- `##` 소제목 두 개에 `keyword` 또는 그 핵심어를 넣습니다.
- 본문에서 `keyword`가 **정확히 일치하는 형태로 나오는 것은 2~3회면 충분**합니다.
  롱테일 키워드는 길기 때문에 그 이상 그대로 반복하면 문장이 어색해지고 어뷰징으로 판정될 수 있습니다.
  대신 연관어로 변주합니다. (억새 → 억새밭, 억새축제 / 단풍 → 단풍철, 색이 오르다)
  즉 `title`·`description`·첫 문단·소제목에는 정확 일치로 넣되, 본문 나머지는 자연스러운 변주로 채웁니다.

**FAQ는 실제 검색 질의 형태로 씁니다.**
네이버는 질문형 검색 비중이 높습니다. `~는 언제 가는 것이 좋나요`, `주차는 어떻게 하나요`,
`대중교통으로 갈 수 있나요`, `유모차로 다닐 수 있나요` 처럼 사람들이 실제로 검색창에 치는
문장을 그대로 질문으로 삼습니다. 추상적인 질문(`어떤 매력이 있나요`)은 유입에 도움이 되지 않습니다.

**시즌 콘텐츠는 시즌 한 달 전에 올립니다.**
색인되고 순위가 잡히는 데 시간이 걸리므로, 단풍 글을 단풍철에 올리면 이미 늦습니다.
`pubDate`는 실제 작성일을 넣되, 시즌 키워드는 시즌 직전에 미리 작성합니다.

## 6. 문체

| 위치 | 문체 |
| --- | --- |
| 본문 | 평서체 (`~다`, `~편이다`, `~것이 좋다`) |
| FAQ 답변 | 존댓말 (`~합니다`, `~좋습니다`) |
| 마무리 고지 문단 | 존댓말 |

추가로:

- 1인칭("제가", "저는")과 2인칭 호칭("여러분")을 쓰지 않습니다.
- 감탄/과장 표현을 쓰지 않습니다. "최고의", "꼭 가봐야 할", "강추" 금지.
- 불릿 리스트는 쓰지 않습니다. 나열이 필요하면 문단이나 표로 처리합니다.
- 이모지를 쓰지 않습니다.

## 7. 사실 정확도 — 가장 중요한 규칙

이 사이트의 글은 역 이름, 노선, 환승, 구간 같은 **확인 가능한 사실**을 담습니다.
지어내면 안 됩니다. 확신이 없으면 **쓰지 말고 빼는 쪽**을 택합니다.

**써도 되는 것** — 쉽게 바뀌지 않는 구조적 사실

- 역 이름과 운영 회사 (예: 난카이 난바역과 오사카 메트로 난바역은 별개다)
- 노선 연결 관계와 환승 필요 여부
- 지역의 대략적 성격 (번화가인지, 주거지인지, 야간 유동인구가 많은지)
- "확인하는 것이 좋다" 형태의 체크 항목

**쓰면 안 되는 것** — 자주 바뀌거나 검증이 필요한 것

- 요금, 가격, 할인율, 숙박비 시세
- 운영시간, 휴무일, 배차 간격
- "도보 7분", "35분 소요" 같은 구체적 소요 시간·거리
  (기존 글의 "약 15km"처럼 널리 알려진 총 길이 정도는 예외)
- 특정 숙소·호텔·브랜드의 이름과 평가
- 통계 수치, 순위, 방문자 수

시간이나 거리를 언급해야 하면 수치 대신 상대적으로 씁니다.
→ "우메다보다 이동 시간이 다소 더 걸리는 편이다"

## 8. 완료 기준

푸시 전에 아래를 모두 만족해야 합니다.

1. `npm run build` 가 에러 없이 통과 (frontmatter 스키마 검증이 여기서 걸립니다)
2. 생성된 페이지가 `dist/` 에 정상 출력됨
3. 본문에 H1 없음, 불릿 없음, 이모지 없음
4. FAQ 4~6개, 체크리스트 표 6행
5. 7장의 "쓰면 안 되는 것"에 해당하는 문장이 하나도 없음

커밋 메시지는 기존 형식을 따릅니다.

```
content: add 도쿄 신주쿠 숙소 가이드
```

한 커밋에 한 편, 또는 같은 도시의 여러 편을 한 커밋에 묶습니다.

## 11. 이미지

글마다 이미지 2장이 붙습니다. 사진이 아니라 **생성한 그래픽**입니다.

| 종류 | 경로 | 크기 | 쓰이는 곳 |
| --- | --- | --- | --- |
| 썸네일 | `/images/thumb/<slug>.png` | 1200×630 | og:image(공유 썸네일), 목록 카드 |
| 본문 도식 | `/images/route/<slug>.png` | 1600×440 | 본문 중간 |

### 만드는 방법

`scripts/image-data.json`에 slug를 키로 항목을 추가한 뒤 `npm run images`를 실행하면
두 장이 함께 생성됩니다. 직접 그리지 않습니다.

```json
"<slug>": {
  "category": "여행 정보",
  "title": "썸네일에 크게 들어갈 제목",
  "keyword": "썸네일 하단에 들어갈 부제",
  "diagram": {
    "heading": "도식 제목",
    "nodes": ["단계 1", "단계 2", "단계 3"],
    "note": "도식 아래 한 줄 설명"
  }
}
```

- `mode`를 `"group"`으로 주면 화살표 없이 나란히 놓입니다. 순서가 아니라 **비교**일 때 씁니다.
  (예: 이름이 비슷한 역 네 곳을 나열하는 경우)
- `nodes`는 3~5개. 각 항목은 짧게 씁니다. 길면 글자가 작아집니다.

### 본문에 넣는 형태

첫 번째 `##` 섹션이 끝나는 지점, 즉 **두 번째 `##` 바로 앞**에 넣습니다.

```html
<figure class="article-figure">
	<img
		src="/images/route/<slug>.png"
		alt="<도식 제목>을 단계별로 정리한 도식 - <keyword>"
		width="1600"
		height="440"
		loading="lazy"
		decoding="async"
	/>
	<figcaption><도식의 note와 같은 문장></figcaption>
</figure>
```

frontmatter에는 썸네일을 넣습니다.

```yaml
heroImage: '/images/thumb/<slug>.png'
heroImageAlt: '<keyword> 정보 가이드 썸네일 이미지'
```

### 규칙

- **`alt`에 `keyword`가 반드시 들어가야 합니다.** 네이버 이미지 검색은 alt를 직접 읽습니다.
- **`figcaption`은 이미지 안 문장과 같게 씁니다.** 이미지 속 글자는 검색엔진이 읽지 못하므로,
  같은 내용을 본문 텍스트로 한 번 더 남겨야 합니다.
- **도식에 새로운 사실을 넣지 않습니다.** 본문에 이미 쓴 내용만 도식으로 옮깁니다.
  도식은 요약이지 추가 정보가 아닙니다.
- `width`와 `height`를 반드시 지정합니다. 없으면 로딩 중 화면이 밀립니다.
